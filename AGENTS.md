## Architecture rules

- Login is WhatsApp OTP or a device PIN: `src/lib/otp.functions.ts` (public server fns, service-role inside handlers) verifies the code, self-registers new numbers (auth user `<mobile>@app.sunrich.local` + `user_profiles` row, company code `SUNRICH`), and `pinLogin` calls the service-role `check_pin` RPC; both return a magic-link token_hash the browser exchanges for a session, then call `record_login` (`otp_whatsapp` / `pin`). The gate in `_authenticated/route.tsx` signs out when the `user_sessions` row is missing or revoked and redirects profiles without a `customer_id` to `/registration`. Why: customers have no passwords, new numbers must be able to sign up, and admins must be able to force logout.
- Device identity and PIN: `src/lib/device.ts` keeps a random `sunrich_device_id` and `sunrich_last_mobile` in localStorage. After every OTP login the app requires `set_my_pin` (via the RPC; any 4 digits are accepted — no weak-PIN rejection) when the device isn't in `user_devices` or the user tapped "Forgot PIN"; PIN login only works on that trusted device. Why: PIN is a device-bound backup to WhatsApp OTP.
- Auth gate lives in `src/routes/_authenticated/route.tsx` (`ssr: false`, redirect to `/auth`); every post-login screen is a child of it. Why: the session lives in browser storage, so gating must run client-side on this external-Supabase project.
- Server reads for signed-in data go through `createServerFn` in `src/lib/` with `.middleware([requireSupabaseAuth])`; the bearer token is attached by `attachSupabaseAuth` in `src/start.ts`. Why: server functions are callable without the route gate.
- All screens apply the saved language on mount via the `useLang` hook (`src/hooks/use-lang.ts`). Why: only the language-picker route seeds the language otherwise.
- Catalogue, product, cart and favourites read the live catalogue only through `fetchCatalogue()` in `src/lib/catalogue.ts`, which calls the authenticated `my_catalogue` RPC (requires `my_session_is_valid`) and caches the last good copy; favourites go through the `toggle_favourite` RPC. Never query price-plan/catalogue tables directly, and never create new database objects. Why: the backend is user-managed and pre-seeded.
- Home renders hero, sections, categories and banners from the existing `app_hero`, `app_home_sections`, `product_categories` and `app_banners` tables (fetched with the same server function as the catalogue). Product image URLs are null; bundled fallback images keyed by product code cover them. Why: the backend is user-managed; the Home design must survive a content-source swap.
- Cart quantities are a single `useCart` hook (`src/hooks/use-cart.ts`) persisted in localStorage under `sunrich.cart`, shared by Home's cart bar and the `/cart` screen. Why: the cart must survive reloads and stay in sync across screens.
- Registration is a 3-step wizard (`_authenticated/registration.tsx`) backed ONLY by existing DB objects: reads via `src/lib/registration.functions.ts` (`listCustomerTypes`, `getMyRegistration`, `getDocumentRequirements`), writes via the `start_registration`, `add_customer_document`, `submit_registration` RPCs; document files upload to the existing private `customer-docs` bucket at `<customer_id>/<uuid>.<ext>`. Never create tables/functions/policies for registration. Status flow drives the gate in `_authenticated/route.tsx`: null/draft/rejected → `/registration`, `blocked` → `/hold`, `active`/`pending_approval` → Home (pending shows the under-review banner and blocks checkout). Why: the backend is user-managed and pre-seeded; the app must work against its schema unchanged.
- Account and Help & queries read `customer_queries`/`customer_query_messages`/`user_profiles` directly through the browser Supabase client — existing RLS scopes every read to the signed-in customer. Replies go through the `reply_query` RPC (staff reply → status `open`, customer reply → `answered`); attachments upload to `customer-docs` at `<customer_id>/queries/<timestamp>-<file>` (storage policy allows it only while the query is open or the registration is editable), avatar photos upload to the public `avatars` bucket at `<user_id>/<file>` and name/photo changes go through `update_my_profile`. Never create tables/functions/policies for these. Why: the backend is user-managed and pre-seeded.
- Profile photo: the Account avatar opens a photo sheet (`PhotoCrop.tsx`, react-easy-crop; 512×512 JPEG < 300 KB) and uploads to the existing public `avatars` bucket at EXACTLY `<user_id>/avatar-<timestamp>.jpg` (upsert false), saving via `update_my_profile(p_full_name, p_photo_url, p_language)`; the previous avatar file is deleted after a successful swap. Removing a photo must go through `clearMyPhoto` in `src/lib/profile.functions.ts` — the RPC coalesces a null `p_photo_url` and RLS has no own-update policy on `user_profiles`. Why: backend is user-managed; only this server fn can null the column for the signed-in user.
- Staff names in query threads come from `getStaffNames` in `src/lib/query-staff.functions.ts`: it first confirms the caller owns the query through RLS on `customer_queries`, then reads staff `user_profiles` names with the service role. Why: customers cannot select other users' profile rows, so the name cannot be fetched client-side.

- `/auth`'s beforeLoad redirect to Home/Registration is skipped while a login is in progress (`sessionStorage` key `sunrich.authflow`, set before the magic-link exchange, cleared in `routeAfterLogin`). Why: otherwise the signed-in redirect fires the moment the session exists and skips the mandatory Set PIN screen on new devices.
- Offline mode: every mutating screen (auth, registration, account, queries, cart, product) disables its actions and shows `offline.hint` while `useOffline()` is false; catalogue screens fall back to the cached read-only copy. Why: this app is used on patchy mobile data.

- Segment-nested route files (track.tsx + track.$id.tsx) must have a layout: /track renders <Outlet/> from track.tsx with the list in track.index.tsx; queries already follows this pattern. Why: a parent route without <Outlet/> silently renders the parent page for child paths.
- Shared order/status label helpers live in src/lib/order-format.ts; route files must not import helpers from other route files. Why: cross-imports between route modules obscure the route tree.
- The customer's own-order filter relies on customer_id in ORDER_SELECT; keep it in sync with fetchMyOrders(). Why: RLS returns own + distributor-routed rows, so the client filters routed ones out.
- Bills, receipts, statement and invoices are read in `src/lib/billing.ts` (RLS + `customer_open_bills`/`customer_statement` RPCs); firm header and UPI come from `getInvoiceFirm` in `src/lib/invoice.functions.ts`, which verifies invoice access via RLS before reading `firms`/`firm_bank_accounts` with the service role. Why: customers cannot select firm or bank rows.
- `sunrich_device_id` / `sunrich_last_mobile` are mirrored to cookies and must never be cleared on logout; `verifyOtp` returns `trusted` for the sent device id. Why: PIN login must survive logout and storage loss.
- Form errors use `data-field-error` markers + `scrollToFirstError()` from `src/lib/form-errors.ts`. Why: one consistent jump-to-first-error behaviour across forms.
