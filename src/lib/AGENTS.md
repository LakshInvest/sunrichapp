# src/lib rules

- `otp.functions.ts`: every `user_profiles` lookup by mobile filters `user_type = customer`, OTP rows are `app_login` only and skip staff `user_id`s, new auth users get no `phone`, `check_pin` gets `p_user_type: "customer"`. Why: one mobile may hold a staff and a separate customer account. `sendOtp` returns `use_pin` for `is_demo_mobile` numbers (no WhatsApp); public server fns (service role inside handlers); `pinLogin` calls service-role `check_pin`; `verifyOtp` returns `trusted` for the sent device id. Why: no passwords; server decides device trust.
- `catalogue.ts` `fetchCatalogue()` is the only catalogue source (authenticated `my_catalogue` RPC, caches last good copy, served without network when under 5 min old unless `{force:true}`; `arrangeCatalogue` sorts by category then product sort_order and drops empty categories); favourites via `toggle_favourite`; Home content from `app_hero`, `app_home_sections`, `product_categories`, `app_banners`; null image URLs use bundled fallbacks by product code. Why: never query price-plan tables directly.
- `registration.functions.ts` reads; writes via `start_registration`, `add_customer_document`, `submit_registration`; docs upload to `customer-docs` at `<customer_id>/<uuid>.<ext>`. Why: existing schema only.
- `profile.functions.ts` `clearMyPhoto` is the only way to null a photo (RPC coalesces null; no own-update RLS). Avatars: `avatars` bucket at exactly `<user_id>/avatar-<timestamp>.jpg`, 512×512 JPEG < 300 KB, old file deleted after swap. Why: backend constraints.
- `query-staff.functions.ts` `getStaffNames`, `invoice.functions.ts` `getInvoiceFirm`, `payments.functions.ts` `getFirmPaymentInfo` and `pod.functions.ts` `getPodUrls` verify access via RLS, then read `user_profiles` / `firms`+`firm_bank_accounts` / `trip_stops`+storage with the service role. POD signature/photo URLs must be signed server-side: the `operations` bucket is staff-only for reads, so the browser cannot sign them. Why: customers cannot select those rows or objects.
- `billing.ts` reads invoices/receipts and `customer_open_bills`/`customer_statement` RPCs. Why: RLS scopes them to the customer.
- `orders.ts`: own-order filter relies on `customer_id` in ORDER_SELECT; keep it in sync with `fetchMyOrders()`. Shared order/status label helpers live in `order-format.ts`. Why: RLS also returns distributor-routed rows.
- `app-settings.ts` is the only reader of Command Center `app_settings`; screens use `useAppSettings()` and its pure rule helpers. Why: one cache, testable rules.
- `ist.ts` is the only source of "today", day starts/ends and month ranges: all day boundaries and date displays are Asia/Kolkata (`istToday`, `istDayStart/End`, `IST_TZ`), and date-only strings count as their own day. Why: a payment at 1:30 AM IST must belong to that IST day, not the previous UTC day.
- `native.ts` wraps Capacitor and must stay a no-op on the web; plugins are imported dynamically. Why: the web app must not depend on native APIs.
- `quoteMyOrder` re-reads `credit_status` per firm in the quote (firm-specific limit beats the customer limit, as in `_create_orders`). Why: the firm-less quote figure disagreed with what the server holds.
- Demo behaviour (`useIsDemo`) comes only from `customers.is_demo`, never `user_profiles.is_demo`. Why: QA accounts use fixed-PIN login but must behave like real shops.
